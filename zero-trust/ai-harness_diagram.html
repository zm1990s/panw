Step 1 · Foundation
The Bare Model Call
No loop. No tools. No memory. One message in, one response out. This confirms the API works and is the primitive everything else builds on.
User message
→
Claude API
→
Single text reply
response = client.messages.create( model=MODEL, max_tokens=512, messages=[{"role": "user", "content": "What is 2+2?"}], ) print(response.content[0].text) # "4"
What you get
  • ✓ Confirmation the API key works
  • ✓ A baseline response to compare against
  • ✓ The simplest possible mental model
What's missing
  • ✗ No loop → can't do multi-step tasks
  • ✗ No tools → can't act on the world
  • ✗ No memory → forgets everything
💡The model replies once and stops. Every subsequent step is scaffolding layered around this single call — the call itself never changes.
Step 2 · Core

while True: response = client.messages.create(...) if response.stop_reason != "tool_use": break for block in response.content: if block.type == "tool_use": out = execute_tool( block.name, block.input) messages.append({ "role": "user", "content": [{ "type": "tool_result", "tool_use_id": block.id, "content": out, }] })
🔄The loop is identical every time. Steps 3–7 only change what the agent is asked to do and what tools it has — the loop code is untouched.

🎯You don't beat prompt injection with a cleverer prompt. You beat it by constraining what tools may do. The model was influenced — the harness bounded the blast radius. That is the defence: least privilege, not a better prompt.
Challenge
Steer the Agent with a Prompt
Same loop, same toolbox — only the system prompt changes, and the result changes completely. auth.py hides a hardcoded master password. Your job: write the prompt that finds it.
❌ Starter prompt (off-target)
"You are a technical writer. In one short paragraph, tell end users what this login feature does. Focus on features, not on code or security."
→ Agent writes marketing copy, misses the vulnerability.
✓ A prompt that cracks it
"You are a security auditor. Inspect auth.py's login logic and report any way to authenticate without the correct password. Cite as file:line."
→ Agent finds RECOVERY_TOKEN: universal master password.
# auth.py — the hidden flaw RECOVERY_TOKEN = "rt-2f9c1a7e" # hardcoded master password def check_login(username, password): if password == RECOVERY_TOKEN: return True # ← any username logs in! def is_admin(username): return username.startswith("admin") # ← trivially spoofable
🔑The toolbox decides what the agent can do. The prompt decides what it will do. Two separate levers, separately optimised.
Hands-On
Write Your Own Tool
A tool is three pieces kept in sync. register_tool() wires all three from one function and a good description.
1
Python function
The code that actually runs when the model requests the tool.
2
JSON Schema
What the model sees: name, description, parameters. The model never reads the function body — this text IS the contract.
3
Dispatch entry
The TOOL_FUNCTIONS table that routes a tool_use block to the right Python function at runtime.
# Manual — 3 pieces in sync def count_lines(path): text = read_file(path) return str(len(text.splitlines())) TOOLS.append({ "name": "count_lines", "description": "...", "input_schema": { ... }, }) TOOL_FUNCTIONS["count_lines"] = count_lines
# register_tool() — one step def count_lines(path): text = read_file(path) return str(len(text.splitlines())) register_tool( count_lines, description="Count lines in a file.", param_descriptions={ "path": "Relative to repo root."} )
📝A tool's description is its reliability. The model never sees the function body — only the name and description. That text is the entire contract with the model.
