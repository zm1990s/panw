五种 MCP 后端认证方式

对比 AI Gateway → MCP（Leg 2）：入口身份验证与 Access Policy 在 Gateway 内统一执行，后端凭据按连接独立配置。

方式 / 服务Gateway 如何准备凭据发给 MCP 的内容MCP 如何校验身份与用途
Claimsmcp-claims · 8000Gateway 自动将入口身份映射为 Claims HeaderX-User-Claims当前仅解析与展示；不验签、不检查有效期观察 Gateway 传入的用户信息get-claims 身份诊断工具
OAuthMCP_OAUTH · 8001Gateway 发起授权码流程并换取用户 Access TokenAuthorization Code Flow + PKCE；用户在 Entra 完成授权Authorization: Bearer T_backendJWT 签名、issuer、有效期及配置的 audience用户委托身份访问 Business API，业务侧继续校验权限
Client CredentialsMCP_OAUTH_CC · 8002Gateway 使用 Client ID + Secret 向 Entra 获取应用 Access TokenClient Credentials FlowAuthorization: Bearer T_appJWT 验签与应用身份检查；按配置检查应用角色 / 客户端白名单Machine / app-only 身份无用户委托；Panda AI 模拟计划与状态工具
NoneMCP_NOAUTH · 8003Gateway 不附加后端认证凭据不附加后端认证信息无需认证，直接执行工具后端匿名访问Palo Alto 产品目录工具
Header KeyMCP_HEADER · 8004Gateway 使用连接配置中的共享 Header 密钥X-MCP-API-Key: <key>与服务端配置的密钥进行恒定时间比对持有共享密钥的调用方模拟 HR 制度与入职清单工具
OAuth / CC 均先由 Gateway 从 Entra 获得后端 Access Token，再调用 MCP；有效 Token 可缓存复用。OAuth 可在获得 refresh token 时刷新，CC 到期后重新申请。Claims 的解析结果不等同于已验证身份。OAuth MCP 调用 Business API 时另携带原始用户 Bearer Token 与 X-Internal-Auth；Header 名称可配置。
